# موقع ماين ستريم | Mainstream

موقع الوكالة الكامل: صفحات عامة (الرئيسية، الخدمات، الأعمال، الخصوصية)، نموذج تواصل يحفظ الطلبات في قاعدة بيانات، ولوحة إدارة عربية على `/admin`.

- **التقنية:** Next.js 16 (يشتغل على سيرفر Node)، PostgreSQL، بدون خدمات خارجية إلزامية.
- **اللغة:** عربي RTL.
- **النسخة القديمة (صفحة العرض الثابتة):** محفوظة في الفرع `backup/static-site-2026-11-14`.

## 1. التشغيل على جهازك

تحتاج Node.js 20 أو أحدث، و PostgreSQL 14 أو أحدث.

```bash
npm install
cp .env.example .env.local      # ثم عبّ DATABASE_URL و INSECURE_COOKIES=1
npm run db:migrate              # ينشئ الجداول
npm run db:seed                 # يحمّل المحتوى الأولي (الخدمات، الأعمال، الأسئلة)
npm run admin:create -- admin "اسمك" owner
npm run dev                     # http://localhost:3000
```

`INSECURE_COOKIES=1` للتشغيل المحلي على http فقط. لا تستخدمه في الإنتاج.

## 2. قاعدة البيانات

- الجداول معرّفة في `db/migrations/*.sql`. أي تغيير جديد يُضاف كملف جديد برقم أعلى (مثل `002_...sql`).
- `npm run db:migrate` يطبّق الملفات اللي ما انطبقت فقط، وكل ملف داخل transaction.
- `npm run db:seed` يضيف المحتوى الأولي بدون ما يلمس الصفوف الموجودة. بعد أول تشغيل يتعدل المحتوى من اللوحة.
- **افصل البيئات:** قاعدة مستقلة لكل من التطوير، التجربة (staging)، والإنتاج. لا تشغّل الاختبارات على قاعدة الإنتاج (الاختبارات تمسح القاعدة).

الجداول الأساسية: `requests` (الطلبات)، `request_notes`، `users`، `sessions`، `audit_log` (سجل التغييرات)، `services`، `works`، `faqs`، `media`، `settings`، `events` (عدّادات مجهولة)، `rate_limits`.

## 3. إنشاء أول مدير

ما فيه تسجيل عام، والعميل ما يحتاج حساب عشان يرسل طلب. الحسابات للموظفين فقط، وأول حساب ينشأ من السيرفر:

```bash
npm run admin:create -- admin "اسم المالك" owner
```

- `admin` هو اسم المستخدم (حروف إنجليزية صغيرة وأرقام، ويُسمح بـ `.` `_` `-`).
- يطبع كلمة مرور مؤقتة مرة وحدة (أو حدّدها بمتغير `ADMIN_PASSWORD`، 12 حرف أو أكثر).
- بعدها ادخل على `/admin`، غيّر كلمة المرور من «حسابي»، وأنشئ اسم مستخدم وكلمة مرور لكل موظف من «المستخدمون».
- **إذا نسي المالك كلمة المرور:** أعد تشغيل نفس الأمر لنفس اسم المستخدم؛ يصفّرها. لباقي الموظفين: المالك يغيّرها من اللوحة.

## 4. الأدوار والصلاحيات

| الدور | الطلبات وبيانات العملاء | المحتوى (خدمات، أعمال، أسئلة، روابط) | المستخدمون، سجل التغييرات، إعدادات النظام | حذف طلب |
|---|---|---|---|---|
| مالك `owner` | ✔ | ✔ | ✔ | ✔ |
| مسؤول متابعة `agent` | ✔ (عرض، حالة، إسناد، ملاحظات) | ✘ | ✘ | ✘ |
| محرر محتوى `editor` | ✘ | ✔ | ✘ | ✘ |

الصلاحية تُفحص على السيرفر في كل صفحة وكل عملية (`requireUser` في `lib/auth.ts`)، مو بإخفاء الأزرار فقط.

الدخول باسم مستخدم وكلمة مرور (12 حرف أو أكثر) ينشئها المالك لكل موظف. حماية الدخول: قفل الحساب 15 دقيقة بعد 5 محاولات خاطئة، حد للمحاولات من نفس العنوان، جلسة تنتهي بعد 12 ساعة أو ساعتين خمول، وكل تغيير صلاحية يسجّل خروج صاحبه.

## 5. متغيرات البيئة

الأسماء كلها في `.env.example`. لا تضع القيم في المستودع.

| المتغير | وش يسوي |
|---|---|
| `DATABASE_URL` | رابط PostgreSQL |
| `APP_SECRET` | مفتاح سري عشوائي (32 حرف أو أكثر). **إلزامي في الإنتاج.** ولّده بـ `openssl rand -base64 48` |
| `SITE_URL` | الرابط العام بدون `/` في النهاية، مثل `https://example.com` |
| `SITE_NOINDEX` | `1` في بيئة التجربة لمنع الفهرسة |
| `SMTP_HOST` `SMTP_PORT` `SMTP_USER` `SMTP_PASS` `SMTP_FROM` | بريد التنبيهات. من لوحة مزوّد بريد الدومين |
| `NOTIFY_EMAIL` | بريد الاستقبال الافتراضي (يتغير من اللوحة: الإعدادات) |
| `UPLOAD_DIR` | مجلد الملفات المرفوعة من اللوحة |

إذا SMTP غير مضبوط: الطلبات تنحفظ عادي، والتنبيه يظهر «فشل» في اللوحة مع زر «أعد إرسال التنبيه».

## 6. النشر على سيرفر

الطريقة المجهزة: سيرفر واحد (VPS) عليه Docker، يشغّل الموقع + PostgreSQL + Caddy (شهادة HTTPS تلقائية).

التكلفة المتوقعة: سيرفر 2GB بحدود 5 إلى 10 دولار شهرياً، زائد الدومين. البريد عبر مزوّد إيميل الدومين.

```bash
# على السيرفر
git clone <repo> mainstream && cd mainstream
cp .env.example .env
# عبّ في .env: APP_SECRET, SMTP_*, NOTIFY_EMAIL وأضف:
#   DOMAIN=example.com
#   POSTGRES_PASSWORD=<كلمة مرور قوية>
docker compose up -d --build        # يبني، يطبّق migrations، ويشغّل
docker compose exec app npm run db:seed
docker compose exec app npm run admin:create -- admin "اسم المالك" owner
```

- وجّه سجل DNS من نوع A للدومين (و `www`) إلى عنوان السيرفر قبل التشغيل، عشان Caddy يصدر الشهادة.
- افتح المنفذين 80 و 443 فقط. منفذ الموقع 3000 وقاعدة البيانات غير مكشوفين للخارج.
- **التحديث:** `git pull && docker compose up -d --build`.
- **بيئة تجربة:** نفس الخطوات على دومين فرعي (مثل `staging.example.com`) بقاعدة مستقلة و `SITE_NOINDEX=1`.

> ملف Docker ما تجرّب بناؤه في بيئة التطوير (Docker غير متاح فيها). أول بناء على السيرفر هو أول تجربة له.

بديل بدون Docker: أي استضافة تشغّل Node 20+ بأمر `npm run build && npm run db:migrate && npm run start`، مع PostgreSQL (مثل Supabase أو Neon) ومجلد دائم لـ `UPLOAD_DIR`، وبروكسي HTTPS قدّامها.

## 7. الدومين و SEO و Search Console

الموجود في الكود:

- عنوان ووصف و canonical ووسوم مشاركة لكل صفحة، وبيانات منظمة (Organization, Service, FAQ, Breadcrumb).
- `/sitemap.xml` و `/robots.txt` يتولدون من المحتوى المنشور على `SITE_URL`. اللوحة والـ API مستبعدين.
- الروابط القديمة `/BILAL/...` تتحول تحويل دائم (308) لنفس المسار على الدومين الجديد.

خطوات الإطلاق (بعد اعتماد الدومين):

1. اضبط `SITE_URL` و `DOMAIN` على الدومين النهائي وانشر.
2. تحويل رابط GitHub Pages القديم: في `deploy/github-pages-redirect/index.html` استبدل `NEW_DOMAIN`، وانشره كـ `index.html` و `404.html` على فرع `gh-pages`. (GitHub Pages ما يدعم تحويل 301 من السيرفر، فهذا أفضل المتاح.)
3. [Google Search Console](https://search.google.com/search-console): أضف خاصية «نطاق»، وأثبت الملكية بسجل TXT في DNS.
4. من «ملفات Sitemap» أرسل: `https://الدومين/sitemap.xml`.
5. من «فحص عنوان URL» اطلب فهرسة الرئيسية وصفحات الخدمات.
6. أنشئ أو حدّث ملف النشاط التجاري على خرائط Google بنفس الاسم والرقم والرابط.

قياس التحويل: كل طلب محفوظ ونقرة «تابع على واتساب» يُسجَّل كحدثين مستقلين (`request_saved` و `whatsapp_click`) مع نوع الطلب والخدمة والصفحة فقط، ويظهر عددهم في نظرة اللوحة العامة. ونفس الحدثين يُدفعان إلى `window.dataLayer` إذا أضفت Google Tag Manager لاحقاً. بيانات العميل ما تُرسل لأي أداة تحليل.

## 8. المراقبة

- `GET /api/health` يرجع 200 إذا الموقع متصل بقاعدة البيانات. اربطه بخدمة مراقبة (مثل UptimeRobot) كل 5 دقايق.
- أخطاء إرسال التنبيهات تظهر في اللوحة (نظرة عامة: «تنبيهات بريد فشلت») وتُكتب في سجل السيرفر بدون بيانات العميل: `docker compose logs app | grep notify_failed`.
- «سجل التغييرات» في اللوحة (للمالك): الدخول، محاولات الدخول الفاشلة، تغييرات الصلاحيات، حالات الطلبات، ونشر المحتوى.

## 9. النسخ الاحتياطي والاستعادة

```bash
# نسخة: قاعدة البيانات + الملفات المرفوعة، وتحتفظ بآخر 14 نسخة
DATABASE_URL=... UPLOAD_DIR=... sh scripts/backup.sh

# استعادة (تستبدل محتوى القاعدة المحددة)
DATABASE_URL=... UPLOAD_DIR=... sh scripts/restore.sh backups/db-XXXX.dump backups/uploads-XXXX.tar.gz
```

مع Docker Compose:

```bash
docker compose exec -T db pg_dump -U mainstream -Fc mainstream > backups/db-$(date +%F).dump
docker compose run --rm -v "$PWD/backups:/backups" app tar -czf /backups/uploads-$(date +%F).tar.gz -C /data/uploads .
```

- شغّل النسخ يومياً بـ cron، **وانسخ مجلد `backups` خارج السيرفر** (تخزين سحابي أو جهاز ثاني).
- جرّب الاستعادة على قاعدة تجربة كل فترة. جُرّبت الاستعادة في بيئة التطوير: نسخة ثم استعادة في قاعدة فاضية، وتطابقت الأعداد والأرقام المرجعية.

## 10. الخصوصية والاحتفاظ بالبيانات

- صفحة `/privacy` تشرح البيانات المجموعة والغرض منها، وتعرض مدة الاحتفاظ الفعلية من الإعدادات.
- مدة الاحتفاظ تتغير من اللوحة (الإعدادات ← حذف الطلبات المغلقة بعد كم يوم؛ `0` يوقف الحذف التلقائي).
- الحذف التلقائي ينفذه أمر يومي:

```bash
# cron على السيرفر، كل يوم 3 الفجر
0 3 * * * cd /path/to/mainstream && docker compose exec -T app npm run retention
```

- المالك يقدر يحذف أي طلب يدوياً من صفحته (طلبات الحذف من العملاء).
- عنوان الإنترنت ما ينحفظ؛ ينحفظ منه بصمة مشفّرة فقط لمنع السبام.

## 11. الاختبارات

```bash
npm test                 # اختبارات سريعة بدون قاعدة بيانات

npm run build
TEST_DATABASE_URL=postgres://.../mainstream_test npm run test:data  # استعلامات اللوحة (lib/admin) على قاعدة حقيقية — القاعدة تنمسح!
TEST_DATABASE_URL=postgres://.../mainstream_test npm run test:e2e   # القاعدة تنمسح!
```

اختبار `test:e2e` يشغّل الموقع فعلياً ويفحص: إرسال الطلب من الجوال والرقم المرجعي، الأنواع الأربعة، الحقول الناقصة، منع التكرار، السبام وحد الإرسال، فشل التنبيه وإعادة إرساله، الدخول وقفل الحساب، إنشاء حسابات الموظفين، صلاحيات كل دور، المسودة والمعاينة والنشر، رفع الصور، ملفات SEO، ترويسات الأمان، وسلامة الروابط. يحتاج Playwright (`npm i -D playwright && npx playwright install chromium`).

## 12. بنية المشروع

```
app/(site)/        الصفحات العامة: الرئيسية، services/[slug]، work، privacy
app/admin/         لوحة الإدارة (login والأقسام داخل (panel)) + actions/ (auth, requests, content, settings, users)
app/api/           requests (استقبال النموذج)، events (عدّادات مجهولة)، health
app/media/         تقديم الملفات المرفوعة
components/        مكونات الواجهة (Hero, Nav, Footer, ContactForm, ServiceCards, Works ...)
lib/               db, auth (الجلسات والصلاحيات), rate-limit, audit, crypto, requests (التحقق والحفظ), notify, content, uploads
lib/intents.ts     أنواع الطلبات وحالاتها      lib/dates.ts  تواريخ بتوقيت الرياض
lib/admin/         استعلامات اللوحة (requests, users, content) — الصفحات والعمليات ما تكتب SQL مباشرة
db/migrations/     ملفات SQL للجداول          db/seed-data.ts  المحتوى الأولي
scripts/           migrate, seed, create-admin, retention, backup.sh, restore.sh
proxy.ts           ترويسة CSP لكل طلب وحماية أولية لمسار /admin
tests/             unit.test.ts و data.test.ts (طبقة البيانات) و e2e.mjs
deploy/            صفحة تحويل رابط GitHub Pages القديم
```

تعديل المحتوى اليومي (خدمات، أعمال، أسئلة، روابط) يتم من اللوحة بدون لمس الكود. النصوص الثابتة في الرئيسية (الهيرو، «ليش ماين ستريم»، القطاعات، خطوات العمل) في `lib/site.ts` و `app/(site)/page.tsx`.

ملاحظة: `DESIGN.md` و `PRODUCT.md` يوصفون الهوية والتصميم الأصلي وما زالوا مرجع الشكل؛ ما تغيّروا في هذا التحديث.
